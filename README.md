# Авито: кандидатогенерация для поиска услуг

Для каждого поискового запроса бенчмарка решение отбирает до 50 объявлений из
корпуса (189 212 объявлений). Метрика — Recall@50.

## Коротко о решении

Гибридная кандидатогенерация + ранкер:

1. **Локация** — главный сигнал. P(локация объявления | локация поиска)
   выучена по train (+ расстояния между центрами локаций).
2. **Лексический поиск BM25** по леммам (pymorphy3) заголовка, параметров и
   описания объявления.
3. **Нейросетевой поиск (bi-encoder)** — `cointegrated/rubert-tiny2`,
   дообученный на парах «запрос → выбранное объявление» из train.
4. **Похожие запросы из истории (kNN по train)** — дают распределение
   подкатегорий P(microcat | запрос) и объявления, которые выбирали по похожим
   запросам.
5. **LightGBM (lambdarank)** переранжирует объединение кандидатов из всех
   источников (~590 на запрос) по 65 признакам и отдаёт топ-50.

## Результаты на локальной валидации

Recall@50 на 12 000 holdout-запросах (как устроена валидация — ниже).
Для LightGBM — 2-фолдовая кросс-валидация по запросам.

| Вариант | Recall@50 |
|---|---|
| BM25 (заголовок+параметры+описание), без учёта локации | 0.365 |
| BM25 + жёсткий фильтр «совместимые локации» | 0.549 |
| BM25 + мягкий приор `2·log P(локация)` | 0.794 |
| bi-encoder rubert-tiny2 (1 эпоха) + приор локации | 0.861 |
| bi-encoder rubert-tiny2 (2 эпохи) + приор локации | 0.870 |
| **Все генераторы + LightGBM (финальное решение)** | **0.940** |
| Потолок: доля правильных объявлений среди кандидатов (~590 на запрос) | 0.976 |

С перевзвешиванием под долю запросов без фильтров в бенчмарке (63%) финальный
Recall@50 = 0.939. Варианты гиперпараметров ранкера (600/1200 деревьев,
63/127 листьев, binary вместо lambdarank) дают 0.939–0.941 — в пределах шума.

Самые важные признаки ранкера: отставание dense-скора от лучшего кандидата
запроса, ранги по dense и BM25, расстояние до центра локации поиска, покрытие
слов запроса текстом объявления, P(подкатегория | похожие запросы), размер
«рынка» объявлений в локации.

## Что выяснил анализ данных

* **Локация решает.** В 83% пар train объявление лежит в той же локации, что и
  поиск; если локация поиска — город, где есть объявления, то в 93%. Часть
  локаций поиска — регионы («Москва и область»): объявлений с таким id нет, и
  выбор распределён по городам региона. Для 17% запросов бенчмарка локация
  поиска — именно такая региональная.
* **Бенчмарк = «один случайный уникальный текст запроса → одна его группа».**
  Каждый текст запроса в бенчмарке уникален; 37.0% текстов встречаются в train.
  Если взять случайный уникальный текст train, то у него больше одной группы
  с вероятностью 37.4% — почти точное совпадение. По этой схеме построена
  локальная валидация.
* **Корпус не подстроен под запросы бенчмарка**: распределение локаций корпуса
  совпадает с распределением объявлений train (корреляция 0.985), в «маленьких»
  локациях (≤3 объявлений) нет ни одного запроса бенчмарка. Значит, корпус —
  по сути случайная выборка объявлений, и валидация «корпус бенчмарка +
  правильные ответы отложенных запросов» честно воспроизводит сложность задачи.
* **Только 9.6% объявлений корпуса есть в train** — «запомнить» ответы нельзя,
  нужен именно поиск по тексту; история кликов помогает лишь частично.

## Локальная валидация

* Из train откладываются 12 000 «поисковых групп» (группа = уникальная
  комбинация текста, локации, фильтров, категории), по одной на случайный
  уникальный текст. Остальные группы тех же текстов остаются в обучении
  (как в бенчмарке: 38% текстов holdout встречаются в train-части против 37%).
* Все модели (BM25-статистики не зависят от разметки; dense-энкодер, kNN,
  модель локаций, популярность объявлений) обучаются **только на train-части**.
* Корпус для валидации = корпус бенчмарка + правильные ответы holdout.
* Ранкер обучается на holdout с 2-фолдовой кросс-валидацией по запросам,
  Recall@50 считается на отложенном фолде; правильные объявления, не попавшие
  в кандидаты, считаются промахом.
* В holdout доля запросов без фильтров 47%, в бенчмарке 63% — поэтому
  дополнительно печатается Recall, перевзвешенный под долю бенчмарка.

## Как запустить

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
# путь к папке с parquet-файлами (по умолчанию ~/Downloads/dataset)
export AVITO_DATA_DIR=/path/to/dataset
bash run_all.sh
```

Скрипт последовательно выполняет шаги из `src/` и кладёт `answer.csv` в корень
проекта. Промежуточные артефакты — в `work/`. Внешние API не используются;
единственное обращение к сети — однократная загрузка весов
`cointegrated/rubert-tiny2` с HuggingFace (дальше работает из локального кэша).

Время на MacBook с Apple M4 и 16 ГБ памяти — около 70 минут: дообучение
энкодера ~30 мин (GPU через MPS), ранкер ~13 мин, кандидаты ~5 мин, остальное
по 1–3 мин. На CUDA энкодер обучается быстрее; на CPU — заметно медленнее.
Фиксированный seed (42) используется во всех случайных шагах; на разном железе
(MPS / CUDA / CPU) результат дообучения может немного отличаться.

| Шаг | Скрипт | Что делает |
|---|---|---|
| 1 | `prepare.py` | единая таблица объявлений, поисковые группы, holdout |
| 2 | `lemmatize_all.py` | лемматизация текстов (pymorphy3) |
| 3 | `train_dense.py` | дообучение bi-encoder rubert-tiny2 |
| 4 | `knn_queries.py` | похожие запросы из истории → подкатегории, объявления |
| 5 | `encode_dense.py` | эмбеддинги корпуса и запросов |
| 6 | `candidates.py` | кандидаты из всех генераторов + признаки |
| 7 | `rerank.py` | LightGBM, кросс-валидация, `answer.csv` |
| – | `check_answer.py` | проверка формата `answer.csv` |

Вспомогательные модули: `config.py` (пути), `common.py` (загрузка, метрика),
`text.py` (нормализация), `bm25.py`, `locations.py`, `dense.py`.
Эксперименты, по которым выбирались настройки (в пайплайн не входят):
`exp_bm25.py` (способы учёта локации в BM25), `exp_rerank.py`
(гиперпараметры ранкера).

## Детали генераторов кандидатов

Для каждого запроса скоры считаются по всему корпусу (матричными операциями
пачками по 250 запросов), затем берётся объединение:

| Генератор | Скор | Топ |
|---|---|---|
| `h_bm25` | BM25(заголовок) + 0.5·BM25(параметры) + 0.3·BM25(описание) + 2·log P(лок.) | 300 |
| `h_dense` | 40·cos(запрос, объявление) + 2·log P(лок.) | 300 |
| `h_bm_mc` | `h_bm25` + 2·log P(подкатегория \| похожие запросы) | 200 |
| `h_de_mc` | `h_dense` + 2·log P(подкатегория \| похожие запросы) | 200 |
| `knn` | объявления, выбранные по похожим запросам train | 150 |

Веса (0.5 / 0.3 для полей, 2 для локации, 40 для косинуса) подобраны по
Recall на holdout; итоговое взвешивание сигналов делает ранкер.

Признаки ранкера (65): скоры BM25 по полям и по фильтрам поиска, доля слов
запроса в заголовке и во всём объявлении, косинус энкодера, P(локация),
расстояние, совпадение локации, P(подкатегория), P(вид услуги), kNN-скор,
ранги в каждом генераторе, свойства объявления (рейтинг, отзывы, цена,
удалённая работа, популярность в train), свойства запроса (длина, есть ли
фильтры, региональный ли поиск, размер рынка в локации, близость ближайшего
запроса из истории), а также разница с лучшим кандидатом и ранг внутри
запроса для основных скоров.

## Ограничения и что можно улучшить

* Ранкер обучается всего на 12 000 запросов; увеличение holdout, вероятно,
  добавило бы качества (ценой меньшей обучающей выборки для энкодера).
* ~2.4% правильных объявлений не попадают в кандидаты — в основном это
  «нелокальные» выборы (поиск по всей России, соседний регион).
* Более крупный энкодер (например, multilingual-e5-small) на Apple M4
  обучается слишком долго (~1 ч на эпоху при нехватке памяти), поэтому
  выбран rubert-tiny2.

## Использованные open-source библиотеки и модели

* [cointegrated/rubert-tiny2](https://huggingface.co/cointegrated/rubert-tiny2)
  — компактный русскоязычный BERT (MIT), базовая модель bi-encoder;
* sentence-transformers, PyTorch, transformers — обучение и инференс энкодера;
* pymorphy3 — лемматизация;
* scikit-learn, SciPy — TF-IDF, разреженные матрицы (BM25 реализован вручную
  поверх scipy.sparse);
* LightGBM — ранкер;
* pandas, NumPy, pyarrow.
