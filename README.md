# Авито: кандидатогенерация для поиска услуг

Для каждого поискового запроса бенчмарка решение отбирает до 50 объявлений из
корпуса (189 212 объявлений). Метрика — Recall@50.

**Кратко:** для каждого запроса собираются ~590 кандидатов из пяти источников
(BM25, дообученный нейросетевой энкодер, похожие запросы из истории — всё с
учётом локации), затем LightGBM выбирает из них топ-50.
Локальная кросс-валидация: **Recall@50 = 0.940**.

---

## Гайд для проверяющего

### Что понадобится

* Python 3.11+ (разработано на 3.13), ~16 ГБ RAM, ~5 ГБ свободного места.
* Данные задачи: `train.parquet`, `benchmark_items.parquet`,
  `benchmark_queries.parquet` в одной папке.
* GPU не нужен для воспроизведения (вариант A). Нужен только для
  переобучения энкодера с нуля (вариант B) — Apple MPS или CUDA.

### Шаг 0. Установка

```bash
git clone https://github.com/alyaalyo/avito_nlp_item_for_queries.git
cd avito_nlp_item_for_queries
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
export AVITO_DATA_DIR=/путь/к/папке/с/parquet   # по умолчанию ~/Downloads/dataset
```

### Вариант A. Точное воспроизведение отправленного `answer.csv` (~10 минут, CPU)

```bash
bash reproduce.sh
```

Что происходит:

1. `prepare.py`, `lemmatize_all.py`, `knn_queries.py` — детерминированная
   подготовка данных (фиксированный seed = 42).
2. `download_artifacts.py` скачивает из
   [GitHub Release v1.0](https://github.com/alyaalyo/avito_nlp_item_for_queries/releases/tag/v1.0)
   обученные артефакты и проверяет их SHA-256:
   `emb_items.npy`, `emb_queries.npy`, `emb_items_ids.parquet` (эмбеддинги
   дообученного энкодера) и `ranker.txt` (LightGBM), ~145 МБ.
3. `candidates.py --split bench` — кандидаты и признаки для запросов бенчмарка.
4. `rerank.py --predict_only` — готовый ранкер пишет `answer.csv`.
5. `check_answer.py` — проверка формата.

Почему артефакты берутся из релиза: дообучение энкодера на GPU не
детерминировано бит-в-бит, поэтому повторное обучение даёт то же качество, но
чуть другой набор объявлений в части строк. Всё, что после эмбеддингов, —
детерминировано.

**Проверка результата.** Контрольная сумма отправленного файла:

```bash
shasum -a 256 answer.csv
# 60f29116e02aa3d7678f0363ff1be8c2b029f4679c97ce05ba3a75b58b60baac
```

Эталонный `answer.csv` также приложен к релизу. Совпадение бит-в-бит проверено
на macOS (Apple Silicon) в чистой рабочей папке. На другой платформе
библиотеки линейной алгебры могут дать отличия в последних знаках косинусов и
поменять местами пару соседних кандидатов — сравнить с эталоном можно так:

```bash
.venv/bin/python src/compare_answers.py answer.csv /путь/к/эталонному/answer.csv
```

Если GitHub недоступен: скачайте файлы со страницы релиза вручную в любую папку
и запустите `bash reproduce.sh --from_dir /эта/папка`.

### Вариант B. Полное обучение с нуля (~70 минут на Apple M4)

```bash
bash run_all.sh
```

Обучает всё заново: энкодер (~30 мин на GPU), kNN, кандидаты, ранкер с
кросс-валидацией (в логе печатается Recall@50 по holdout) и пишет `answer.csv`.
Единственное обращение к сети — однократная загрузка базовой модели
`cointegrated/rubert-tiny2` с HuggingFace. Качество воспроизводится
(Recall@50 ≈ 0.94 на CV), но `answer.csv` может немного отличаться от
отправленного из-за недетерминированности обучения на GPU.

## Описание решения

### 1. Данные и признаки

**Данные.** Train свёрнут в «поисковые группы» — уникальные комбинации текста
запроса, локации, фильтров, категории и флага доставки (так устроена строка
бенчмарка): 354 тыс. групп со списками выбранных объявлений. Из объявлений
используются заголовок, параметры, описание, локация, координаты,
подкатегория, рейтинг, отзывы, цена и флаги.

**Что показал анализ данных:**

* **Локация решает.** В 83% пар train объявление лежит в той же локации, что и
  поиск; если локация поиска — город, где есть объявления, то в 93%. Часть
  локаций поиска — регионы («Москва и область»): объявлений с таким id нет, и
  выбор распределён по городам региона. Для 17% запросов бенчмарка локация
  поиска — именно такая региональная.
* **Бенчмарк = «один случайный уникальный текст запроса → одна его группа».**
  Каждый текст запроса в бенчмарке уникален; 37.0% текстов встречаются в train.
  Если взять случайный уникальный текст train, то у него больше одной группы
  с вероятностью 37.4% — почти точное совпадение.
* **Корпус не подстроен под запросы бенчмарка**: распределение локаций корпуса
  совпадает с распределением объявлений train (корреляция 0.985), в
  локациях с ≤3 объявлениями нет ни одного запроса бенчмарка.
* **Только 9.6% объявлений корпуса есть в train** — «запомнить» ответы нельзя,
  основной сигнал — текстовое соответствие; история кликов помогает частично.

**Признаки ранкера (65):**

* текст: BM25 по заголовку, параметрам и описанию; BM25 фильтров поиска по
  параметрам объявления; доля слов запроса в заголовке и во всём объявлении;
  косинус эмбеддингов энкодера;
* локация: P(локация объявления | локация поиска), расстояние, совпадение
  локации, региональный ли поиск, число объявлений в совместимых локациях;
* категория: P(подкатегория | похожие запросы), P(вид услуги | похожие запросы);
* история: «это объявление выбирали по похожим запросам», популярность
  объявления и подкатегории в train;
* объявление: рейтинг, отзывы, цена, скрытый телефон, запрет сообщений,
  удалённая работа, длина описания;
* запрос: длина, есть ли фильтры, близость ближайшего запроса из истории;
* для основных скоров — разница с лучшим кандидатом запроса и ранг внутри
  запроса (абсолютные скоры плохо сравнимы между запросами).

### 2. Модели и алгоритмы

* Лемматизация pymorphy3; чистка шаблонного шума в параметрах регулярками.
* BM25, реализованный на `scipy.sparse` (скоринг пачки запросов по всему
  корпусу одним матричным умножением).
* Модель локаций: частотная оценка P(локация объявления | локация поиска) по
  train + центры локаций по координатам объявлений.
* Bi-encoder `cointegrated/rubert-tiny2`, дообученный 2 эпохи на парах
  «запрос + фильтры → выбранное объявление» (MultipleNegativesRankingLoss,
  негативы из батча, сэмплер без повторов текстов, ≤30 пар на текст запроса).
  Выбран из-за скорости: на Apple M4 ~1500 объявлений/с против ~300 у
  multilingual-e5-small.
* kNN по TF-IDF (леммы 1–2-граммы + символьные 3–5-граммы) над запросами
  train, K = 40.
* Объединение пяти генераторов кандидатов:

  | Генератор | Скор | Топ |
  |---|---|---|
  | `h_bm25` | BM25(заголовок) + 0.5·BM25(параметры) + 0.3·BM25(описание) + 2·log P(лок.) | 300 |
  | `h_dense` | 40·cos(запрос, объявление) + 2·log P(лок.) | 300 |
  | `h_bm_mc` | `h_bm25` + 2·log P(подкатегория \| похожие запросы) | 200 |
  | `h_de_mc` | `h_dense` + 2·log P(подкатегория \| похожие запросы) | 200 |
  | `knn` | объявления, выбранные по похожим запросам train | 150 |

* LightGBM lambdarank (1000 деревьев, 63 листа) переранжирует кандидатов.

### 3. Как проверялось качество до отправки

* Из train отложены 12 000 групп по схеме бенчмарка: случайный уникальный
  текст → одна его группа, остальные группы текста остаются в обучении
  (38% текстов holdout встречаются в train-части против 37% в бенчмарке).
* Корпус для валидации = корпус бенчмарка + правильные ответы holdout.
* Энкодер, kNN, модель локаций и популярность обучены только на train-части.
* Ранкер — 2-фолдовая кросс-валидация по запросам; правильные объявления, не
  попавшие в кандидаты, считаются промахом.
* В holdout 47% запросов без фильтров, в бенчмарке 63% — дополнительно
  считается Recall, перевзвешенный под бенчмарк.

| Вариант | Recall@50 |
|---|---|
| BM25 без учёта локации | 0.365 |
| BM25 + жёсткий фильтр «совместимые локации» | 0.549 |
| BM25 + мягкий приор `2·log P(локация)` | 0.794 |
| энкодер (1 эпоха) + приор локации | 0.861 |
| энкодер (2 эпохи) + приор локации | 0.870 |
| **все генераторы + LightGBM (финальное решение)** | **0.940** (0.939 с перевзвешиванием) |
| потолок: правильное объявление среди кандидатов | 0.976 |

Варианты гиперпараметров ранкера (600/1200 деревьев, 127 листьев, binary
вместо lambdarank) дают 0.939–0.941 — в пределах шума. Формат `answer.csv`
проверяется скриптом `check_answer.py`.

### 4. Найденные ошибки и что с ними сделано

| Ошибка | Что сделано | Эффект |
|---|---|---|
| жёсткий фильтр по локации терял региональные поиски и соседние города | мягкий приор `2·log P(локация)` + расстояние как признак | 0.549 → 0.794 |
| региональные локации поиска без объявлений | P(локация объявления \| локация поиска) по train | — |
| морфология («видеодомофонов» / «видеодомофон») | лемматизация | — |
| опечатки («мазачкале», «бухгалтерсуое») | символьные n-граммы в kNN, подсловная токенизация энкодера | — |
| синонимы, слов запроса нет в объявлении («выкосить траву» / «покос травы») | дообученный энкодер, подкатегории по похожим запросам | 0.794 → 0.870 |
| шаблонный шум в параметрах объявлений раздувал BM25 | чистка регулярками | — |
| ложные негативы при обучении энкодера (тот же запрос в батче), перекос в частые запросы | батчи без повторов, ≤30 пар на текст | — |
| скоры несравнимы между запросами | относительные признаки внутри запроса | — |

**Остаточные ошибки на holdout:**

* ~2.4% правильных объявлений не попадают в кандидаты. Из 329 таких пар только
  11.5% лежат в локации поиска, а в 24% такая пара «локация поиска → локация
  объявления» ни разу не встречалась в train: поиск «по всей России», соседние
  регионы, шумные клики (запрос «кронирование и спил деревьев» → объявление
  «Тендерный специалист»). Ослабление приора локации вернуло бы часть из них,
  но ухудшает остальные запросы (вес 1 вместо 2: Recall@50 BM25 0.797 → 0.674).
* ~3.5% правильных объявлений есть среди кандидатов, но не попадают в топ-50.

### Ограничения и что можно улучшить

* Ранкер обучается на 12 000 запросах; больший holdout, вероятно, добавил бы
  качества (ценой меньшей выборки для энкодера).
* Более крупный энкодер (multilingual-e5-small) на Apple M4 с 16 ГБ памяти
  обучался слишком медленно, поэтому выбран rubert-tiny2.

## Использованные open-source библиотеки и модели

* [cointegrated/rubert-tiny2](https://huggingface.co/cointegrated/rubert-tiny2)
  — компактный русскоязычный BERT (MIT), базовая модель bi-encoder;
* sentence-transformers, PyTorch, transformers — обучение и инференс энкодера;
* pymorphy3 — лемматизация;
* scikit-learn, SciPy — TF-IDF, разреженные матрицы (BM25 реализован вручную);
* LightGBM — ранкер;
* pandas, NumPy, pyarrow.

Внешние API не используются.
